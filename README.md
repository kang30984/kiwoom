# 시세 터미널

국내(키움증권)와 미국 주식 시세를 한 화면에서 보려고 만든 웹 앱이다. 관심종목, 실시간 현재가, 호가 10단계, 월·주·일·분봉 차트, 거래량·등락률 순위, 그리고 변동성(ATR)으로 손절가와 수량을 계산해 주는 리스크 계산기가 있다.

```
브라우저(React)  ──HTTP/WS──▶  내 서버(Node.js)  ──REST/WS──▶  키움 · 미국 시세 공급자
```

API 키는 서버에만 두고 브라우저는 이 서버하고만 통신한다. 브라우저에서 증권사 API를 바로 부르면 CORS에 막히고 시크릿키도 그대로 노출된다.

## 빠르게 실행해 보기

API 키 없이도 돌아간다. 처음에는 가짜 시세를 만드는 데모 모드로 뜨기 때문에 계좌나 키 없이 기능을 전부 볼 수 있다.

```bash
git clone https://github.com/kang30984/kiwoom.git
cd kiwoom
cp .env.example server/.env

cd server && npm install && npm start   # 터미널 1
cd web    && npm install && npm run dev # 터미널 2
```

브라우저에서 http://localhost:5173 을 연다. Node.js 20 이상이 필요하다(`.nvmrc` 참고).

Windows는 `start.bat`을 더블클릭, macOS/Linux는 `bash start.sh`로 위 과정을 한 번에 할 수 있다. 다른 사람에게 테스트를 부탁할 때는 [START-HERE.md](START-HERE.md)를 먼저 보게 하면 된다.

`.env.example`은 `DEMO=true`로 되어 있다. 이 줄을 지우면 앱키가 있는지 보고 알아서 정한다(키가 없으면 데모). 어떤 모드로 떴는지는 서버 시작 로그나 http://localhost:4000/api/health 의 `demo`, `keyLoaded` 값으로 확인할 수 있다.

## 주의

- 투자 조언을 하는 프로그램이 아니다. 무엇을 사고팔지 방향을 알려 주는 기능은 일부러 넣지 않았다.
- 매매계획의 손절가, 익절가, 수량은 과거 변동성(ATR)으로 기계적으로 계산한 값이다. 가격을 예측한 게 아니고, 그 가격에 간다는 보장도 없다.
- 데모 모드의 숫자는 프로그램이 만든 가짜 값이다.
- 계산된 최대 손실은 상한이 아니다. 갭 하락이 나면 손절가보다 낮은 가격에 체결된다.
- 거래비용과 세율 기본값은 가정한 값이다. 본인 계좌 조건에 맞게 바꿔서 써야 한다.
- 투자 판단과 결과는 본인 책임이다.

## 보안

- `.env`는 커밋하면 안 된다. 키움 앱키·시크릿키와 미국 시세 API 키가 여기에 들어간다. 저장소 루트의 `.gitignore`가 `.env`, `server/.env`, `node_modules/`, `dist/`를 제외하고 있다.
- 클론한 뒤 한 번 확인해 두면 좋다.

  ```bash
  git check-ignore -v server/.env   # 무시 규칙이 출력되면 정상
  git status --short                # 여기에 server/.env 가 보이면 안 된다
  ```

  Windows에서는 `check.bat`이 같은 검사를 해 준다.
- 실수로 커밋했다면 키부터 재발급해야 한다. 커밋 이력에서 파일을 지워도 이미 나간 키는 그대로 유효하다.
- 다른 사람에게 본인 키를 주지 않는다. 호출 한도와 계좌 권한을 같이 쓰게 된다.
- 시세 조회만 하고 주문 기능은 없다.

## 실행 (자세히)

Node.js 20 이상만 있으면 된다([nodejs.org](https://nodejs.org)).

- Windows: `start.bat` 더블클릭
- macOS / Linux: 폴더로 이동해서 `bash start.sh`

스크립트가 `server/.env` 만들기, 패키지 설치, 백엔드 실행, 브라우저 열기까지 해 준다. 처음에는 패키지 설치 때문에 1~2분 걸리고 그다음부터는 몇 초면 뜬다.

직접 하려면 터미널 두 개를 쓴다.

```bash
cp .env.example server/.env

cd server && npm install && npm start     # 터미널 1
cd web && npm install && npm run dev      # 터미널 2
```

화면은 http://localhost:5173, 백엔드는 http://localhost:4000 이다.

### 데모 모드 (기본값)

`.env`가 `DEMO=true`이면 키움에 접속하지 않고 서버가 가짜 시세를 만들어서 보낸다. 가격이 랜덤워크로 움직여서 실시간 깜빡임, 호가창, 차트, 순위가 전부 동작하는 걸 볼 수 있다. 물론 실제 시세는 아니다.

오른쪽 위 표시등이 빨간색이면 실시간 스트림이 연결된 상태다.

### 실제 시세로 바꾸기

1. 키움증권에 로그인해서 오픈API를 신청하고 앱키·시크릿키를 받는다.
2. `server/.env`를 고친다.

   ```ini
   DEMO=false
   KIWOOM_APP_KEY=발급받은_앱키
   KIWOOM_SECRET_KEY=발급받은_시크릿키
   KIWOOM_MOCK=true     # 처음에는 모의투자로 확인하는 게 안전하다
   ```

3. 백엔드를 다시 실행한다.

### 안 될 때

|증상|원인과 해결|
|-|-|
|`백엔드 서버에 연결할 수 없습니다`|백엔드가 안 떠 있다. 터미널에 `서버 실행 http://localhost:4000`이 찍혔는지 본다|
|실시간 표시등이 계속 회색|데모 모드면 바로 켜져야 한다. 실제 모드면 토큰 발급이 실패한 것이니 백엔드 로그를 본다|
|`EADDRINUSE`|4000이나 5173 포트를 다른 프로그램이 쓰고 있다. `.env`의 `PORT`를 바꾼다|
|`'...'은(는) 내부 또는 외부 명령이 아닙니다`가 잔뜩 나옴|`start.bat`이 UTF-8 한글로 저장된 경우다. cmd.exe는 배치 파일을 949 코드페이지로 읽어서 한글이 줄 구조를 깨뜨린다. 영문만 있는 `start.bat`으로 바꾼다|
|지금 어떤 버전이 돌고 있는지 모르겠음|`check.bat`을 실행한다. 화면 왼쪽 위 `ver`와 `/api/health`의 `version`을 비교한다|
|파일을 바꿨는데 화면이 그대로|백엔드가 예전 코드를 메모리에 들고 있다. `Kiwoom Backend` 창을 닫고 `start.bat`을 다시 실행한 뒤 브라우저에서 Ctrl+Shift+R|
|데모 가격이 비정상적으로 큼|백엔드를 다시 실행한다. 가격 상태가 프로세스 메모리에 있다|
|익절가가 `—`이고 `상한가 도달`|현재가가 상한가라 더 오를 수 없는 상태다. 배수를 바꿔도 익절가는 그대로다|
|`Missing script: "dev"`|`web` 폴더 밖에서 실행했다. `cd web` 후 `npm run dev`|
|숫자가 전부 `—`|실제 모드에서 api-id가 맞지 않는다. 아래 "확인이 필요한 부분" 참고|
|검색 결과가 항상 비어 있음|종목 마스터를 못 받은 상태다. 백엔드 로그의 `[master]` 줄을 보고 `ka10099`를 문서와 대조한다|
|종목을 눌렀는데 값이 전부 0|종목코드에 거래소 접미사가 붙었는지 본다(`233740_AL` 같은 형태). ver 13부터는 자동으로 처리한다|
|특정 봉만 비어 있음|해당 api-id를 문서와 대조한다(주봉 `ka10082`, 월봉 `ka10083`)|
|`cp: cannot stat '.env.example'`|저장소 루트가 아닌 곳에서 실행했다. `cd kiwoom` 후 다시 한다|
|`bash start.sh`가 바로 멈춤|`.env.example`이 없으면 최소 설정으로 `server/.env`를 만들고 진행한다. 그래도 멈추면 Node 버전을 확인한다|
|국내 탭 숫자가 비어 있고 로그에 `토큰 발급 실패` 반복|`DEMO=false`인데 앱키가 없다. `DEMO=true`로 바꾸거나 앱키를 넣는다|
|수급 탭 체결강도가 계속 `—`|`FID_STRENGTH`가 문서와 다르다. 0B 주식체결 FID 표와 대조한다|
|프로그램매매 금액이 터무니없이 크거나 작음|`PROGRAM_AMOUNT_UNIT`이 틀렸다. 화면의 `원본 단위 OO 가정`과 실제 응답을 비교한다|
|수급 탭에 계속 `아직 집계되지 않았습니다`|장중이나 휴장일이면 정상이다. 실제 모드에서 계속 그러면 `/api/flow/stats`의 `unverifiedTr`을 문서와 대조한다|
|`알 수 없는 차트 종류`|`CHART_TR`에 없는 타입이다. 응답의 `detail`에 쓸 수 있는 목록이 나온다|
|`git status`에 `server/.env`가 보임|`.gitignore`가 없거나 망가졌다. 커밋하지 말고 `.gitignore`부터 고친다|

## 매매계획 패널 (오른쪽 "매매계획" 탭)

이 기능도 사라 마라를 알려 주지 않는다. 어떤 종목에 들어갈지는 사용자가 정하고, 여기서는 그 결정에 필요한 숫자만 계산한다.

입력은 세 가지다.

|입력|의미|
|-|-|
|투자 가능 자금|이 종목에 넣을 돈이 아니라 리스크 계산의 기준이 되는 전체 자금|
|감당할 손실 %|그중 이번 매매 한 번으로 잃어도 되는 비율. 보통 1~2%|
|ATR 배수|손절폭을 하루 평균 변동폭의 몇 배로 둘지(기본 2)|

계산 순서는 이렇다.

```
ATR(14)  ─×배수─→  손절폭  ─────→  손절가
                     │
                     ├─×1,2,3──→  익절가 1R / 2R / 3R
                     │
                     └─ 감당손실 ÷ 손절폭 ──→ 수량 ──→ 투입금액, 최대손실
```

손절폭을 5% 같은 고정 비율이 아니라 ATR로 잡은 이유가 있다. 하루에 1% 움직이는 종목과 6% 움직이는 종목에 같은 손절폭을 쓰면, 앞의 종목은 손절이 너무 멀어서 손실이 커지고 뒤의 종목은 평소 흔들림에도 손절에 걸린다. ATR 배수를 쓰면 종목마다 실제로 움직이는 폭에 맞춰진다.

1R은 손절폭 1배를 말한다. 손절가까지 2,000원이면 1R 익절은 +2,000원이다. 손익비를 배수로 보면 승률과 같이 계산할 수 있다. 2R을 목표로 하면 승률이 34%만 넘어도 기대값이 플러스가 된다.

### 수량은 두 기준을 같이 보여준다

"살 수 있는 수량" 하나만 보여주면 오해하기 쉽다. 두 기준은 서로 다른 질문에 대한 답이다.

|기준|질문|계산|
|-|-|-|
|자금 전액|돈으로 몇 주까지 살 수 있나|투자금 ÷ 현재가|
|감당 손실|손절됐을 때 정한 금액만 잃으려면 몇 주까지인가|(투자금 × 손실%) ÷ 주당 손절폭|

권장 수량은 둘 중 작은 쪽이다. 돈이 없으면 못 사고, 리스크 한도를 넘기면 처음에 정한 손실 상한이 의미가 없어진다. 어느 쪽이 수량을 제한하고 있는지 표에 표시하고, 자금을 다 썼을 때의 손실도 옆에 같이 보여준다.

예: 현재가 167.5만 원, ATR 12.7%, 자금 1,000만 원, 감당 손실 10%

```
자금 전액     5주   투입 837.5만   손절 시 -213.5만 (자금의 21.3%)
감당 손실 10% 2주   투입 335.0만   손절 시  -85.4만 (자금의  8.5%)
→ 권장 2주
```

반대로 변동성이 낮은 종목은 리스크 기준으로 555주가 나와도 자금으로는 135주밖에 못 살 수 있다. 이때는 135주를 권장한다. 처음에는 555주를 그대로 보여주고 경고만 띄웠는데, 실제로는 살 수 없는 수량을 권장하는 셈이라 고쳤다.

목표가보다 수량이 더 중요하다고 본다. 목표가는 갈지 안 갈지 아무도 모르지만, 수량은 손절됐을 때 잃는 금액을 정해 준다.

손익분기가는 매수 수수료를 내고 들어가서 매도 수수료와 세금을 떼고 나왔을 때 본전이 되는 가격이다.

### 평균단가와 보유 수량은 따로 계산한다

|입력|계산되는 것|
|-|-|
|보유 수량만|평가 금액, 손절되면 잃는 금액|
|평균단가만|현재 손익률, 원금 회복가|
|둘 다|위 전부와 평가손익|

처음에는 `if (avgCost)`가 전체를 감싸고 있어서 평균단가를 비워 두면 보유 수량을 입력해도 아무것도 나오지 않았다. 지금은 입력된 값만으로 계산하고, 빠진 입력이 뭔지 알려준다.

보유분의 `손절 시 손실`은 평가액 대비가 아니라 감당 손실 예산 대비로 보여준다. 평가액 대비로 보면 수량이 약분돼서 손절폭 %와 똑같은 숫자가 나오기 때문이다. 예를 들어 자금 1,000만 원에 감당 손실 2%인 사람이 167만 원짜리 종목을 500주 들고 있으면, 손절 시 예산의 535배를 잃는다. 이미 리스크 한도를 한참 넘었다는 뜻이라 바로 행동으로 이어질 수 있는 정보다. 100%를 넘으면 경고도 띄운다. 비율은 크기에 따라 `<0.1%`, `535%`, `535배`처럼 표기를 바꾼다. 소수점 자리를 고정하면 아주 작은 값이 `0.0%`로 뭉개진다.

### 큰 숫자 표시

합계 금액과 수량은 만·억·조 단위로 줄여서 보여준다. `9,999,999,999,904,000원`을 그대로 두면 자릿수를 세야 한다.

```
      829,000,000원  ->  8.3억원
3,873,831,775,484,000원  ->  3,874조원
        6,031,363,088주  ->  60.3억주
```

가격은 줄이지 않는다. 손절가, 익절가, 현재가는 정확해야 하고 금액이랑 섞이면 헷갈린다. 줄여서 표시한 값에 마우스를 올리면 정확한 값이 나온다. 미국 탭은 `$1.5M`, `$2.3B`처럼 영어 단위를 쓴다.

### 그 밖의 계산 규칙

- 권장 수량이 최근 20일 평균 거래량의 5%를 넘으면 경고한다. 투자금을 잘못 넣으면 4,300만 주 같은 값이 나오는데, 시장에서 소화할 수 없는 규모다.
- 가격은 KRX 호가단위에 맞춘다(손절은 내림, 익절은 올림).
- 익절가를 오늘 가격제한폭으로 자르지 않는다. ±30%는 하루 제한이고 익절 목표는 며칠에 걸쳐 가는 값이다. 상한가로 자르면 배수를 바꿔도 목표가가 다 같은 값이 돼 버린다. 대신 `당일 도달 불가`라고 표시하고 오늘의 상·하한가를 참고로 보여준다.
- 손절가도 하한가로 끌어올리지 않는다. 그렇게 하면 손절폭이 줄어서 수량은 많게, 위험은 작게 계산된다. 리스크 계산기에서 가장 위험한 종류의 오류다.
- 경고 문구의 통화 표기는 시장 설정(`markets.js`의 `money()`, `price()`)에서 가져온다. 문구에 `원`을 박아 두면 미국 탭에서 달러를 원이라고 말하게 된다. 금액 뒤에는 조사(`이/가`)가 붙지 않게 문장을 썼다. 통화 표기에 따라 조사가 달라지기 때문이다.
- `krx.js`의 `DEFAULT_COSTS` 수수료와 세율은 가정값이다. 증권사 수수료는 계좌마다 다르고 세율은 자주 바뀐다.

### 이 계산으로 할 수 없는 것

- 가격 예측은 하지 않는다. ATR은 과거 변동폭일 뿐이다.
- 갭 하락은 막지 못한다. 손절가를 70,300원으로 잡아도 다음 날 68,000원에 시작하면 그 가격에 체결된다.
- 재무, 실적, 뉴스는 보지 않는다.
- 분할 매수·매도, 세금 상세, 신용·미수는 반영하지 않는다.

## 차트

첫 화면은 일봉 1년이다. 봉 종류별 기간은 `config.js`의 `CHART_YEARS`에서 정한다(일봉 1년, 주봉 3년, 월봉 6년). 요청에 `?years=3`을 붙이면 바꿀 수 있다.

키움은 한 번에 주는 행 수가 정해져 있어서 긴 기간은 `cont-yn` 페이징으로 이어 받는다. `fetchCandles`는 원하는 시작일까지 받으면 바로 멈춘다(최대 10페이지). 매매계획은 같은 함수로 일봉 120개만 받는다. ATR(14)과 최근 20일 고저만 쓰기 때문에 더 받아도 결과는 같고 호출만 늘어난다.

종목이나 시장이 바뀌면 새 데이터를 받기 전에 기존 캔들부터 비운다(`setData([])`). 이걸 안 하면 요청이 느리거나 실패했을 때 이전 종목 차트가 그대로 남는다. 실제로 미국 탭에서 국내 탭으로 넘어갔을 때 미국 캔들이 계속 보이는 문제가 있었다. 헤더에 봉 개수(`차트 · 261봉`)를 표시하는 것도 데이터가 덜 왔는지 바로 보려는 것이다.

`lightweight-charts`는 시간이 겹치지 않고 계속 증가해야 제대로 그려진다. 어긋나면 시간축이 `9월 10월 4월 12월`처럼 뒤섞인다. 페이지를 이어 붙이다 보면 같은 날짜가 두 번 들어오거나 순서가 틀어질 수 있어서, 합친 뒤 `normalizeCandles()`로 정렬하고 중복을 지운다.

년봉 같은 새 봉 종류는 두 군데만 고치면 붙는다.

1. `server/src/config.js`의 `TR`에 api-id를 넣고, `routes/chart.js`의 `CHART_TR`에 연결한다.
2. `web/src/components/PriceChart.jsx`의 `PERIODS`에 `['year', '년봉']`을 넣는다.

등록하지 않은 타입으로 요청하면 400과 함께 쓸 수 있는 목록을 돌려준다. 처음에는 모르는 타입이 오면 조용히 일봉을 줬는데, 그러면 화면에 탭만 추가하고 서버 등록을 빠뜨렸을 때 '년봉' 탭에 일봉이 그려져도 알아채기 어려웠다. 데모 모드에서도 보이게 하려면 `demoFeed.js`의 `count`, `shockScale`, `wickScale`에도 항목을 넣는다.

## 종목 검색

입력할 때마다 키움 API를 부르면 호출 한도에 금방 걸린다. 그래서 `ka10099`로 코스피·코스닥 종목 목록을 한 번 받아서 서버 메모리에 12시간 캐시하고, 검색은 그 안에서 한다.

글자를 입력하면 그 글자가 들어간 종목이 아래에 뜨고, 하나를 고르면 검색창에 종목명이 채워진다. `추가`를 눌러야 관심종목에 들어간다. 고르자마자 추가되지 않게 해서 한 번 확인할 수 있게 했다.

정렬 순서는 코드 완전 일치, 이름 완전 일치, 이름 앞부분 일치, 코드 앞부분 일치, 이름 포함 순이다. 순위가 같으면 이름이 짧은 쪽이 위로 온다. `삼성전자`가 `삼성전자우`나 레버리지 ETF보다 먼저 나와야 하기 때문이다.

종목 목록을 아예 못 받은 경우와 검색 결과가 없는 경우는 다른 안내를 보여준다. 목록을 못 받았어도 6자리 코드를 직접 넣으면 추가할 수 있다.

드롭다운 쪽은 생각보다 손이 많이 갔다.

- 종목을 고른 직후 그 이름으로 다시 검색하면 드롭다운이 또 열린다. 처음에는 boolean 플래그로 막았는데, 이미 `삼성전자`를 다 쳐 놓고 목록에서 `삼성전자`를 고르면 값이 같아 effect가 안 돌고 플래그가 남아서 다음 입력을 먹어 버렸다. 지금은 건너뛸 검색어 자체를 `skipQuery`에 담고, 사용자가 직접 입력하면 지운다.
- 고른 뒤 입력창에 다시 포커스가 가면서 `onFocus`가 아직 바뀌지 않은 `items`를 보고 드롭다운을 다시 여는 문제도 있었다. 렌더 조건과 `onFocus` 양쪽에 `!picked` 조건을 넣었고, "없습니다" 안내는 지금 검색어로 검색이 끝났을 때만(`searchedFor === query`) 보여준다.
- 드롭다운이 절대 위치라서 상단 패널에 `overflow: auto`가 걸려 있으면 z-index와 상관없이 잘린다. `.pane--top`만 `overflow: visible`로 두고 z-index를 올렸다.

종목명이 `...`으로 잘렸을 때는 마우스를 올리면 전체 이름이 뜬다(`Truncated`). 관심종목 목록이 `overflow: auto`라 안쪽에 띄우면 잘리기 때문에 `position: fixed`로 띄운다. 실제로 잘렸을 때(`scrollWidth > clientWidth`)만 보여주고, 화면 오른쪽 끝에서는 안쪽으로 당기고, 스크롤하면 닫는다. 키보드 포커스로도 열리고 터치 환경을 위해 `title`도 같이 넣었다.

## 수급 패널 (오른쪽 "수급" 탭)

체결강도와 프로그램 매매 동향을 본다. 국내 탭에만 있다. 체결강도는 미국 무료 API에서 주지 않고, 프로그램매매는 KRX에만 있는 개념이다.

|  | 체결강도 | 프로그램 매매 |
|-|-|-|
| 데이터 | 종목별, 틱 단위 값 | 시장·종목별 집계, 지연 있음 |
| 받는 방법 | 기존 `0B` 실시간 데이터의 필드 하나 | REST 폴링(60~120초) |

체결강도는 `realtime.js`의 FID 맵에 한 줄, 보내는 데이터에 한 줄만 추가하면 됐다. 화면 쪽 `useRealtime.js`는 받은 메시지를 `{ ...before, ...msg }`로 펼쳐 담기 때문에 따로 고칠 필요가 없었다.

### 체결강도는 직접 계산하지 않는다

체결강도는 장 시작부터 누적한 비율이다. 서버에서 직접 쌓으면 오후 2시에 접속한 사람에게는 "접속한 뒤부터의 누계"가 보여서 전혀 다른 숫자가 된다. 종목별 누적 상태, 장 시작 초기화, 재연결 처리까지 붙어서 지금처럼 받은 걸 그대로 흘려보내는 `realtime.js` 구조도 깨진다. 그래서 키움이 주는 값을 그대로 쓰고, 종목을 고를 때 REST로 초기값을 채운 뒤 실시간 값으로 덮어쓴다.

장 시작 직후(09:00~09:05)에는 체결이 몇 건 없어서 400% 같은 값이 나온다. 축은 0~200으로 고정하고 넘는 값은 끝에 붙이며, 표본이 적으면 안내를 띄운다. 데모 피드도 매번 랜덤값을 뽑지 않고 체결량을 누적해서 장 초반에 튀고 점점 안정되게 만들었다. 그래야 데모로도 이 처리를 확인할 수 있다.

호가 탭의 `매수 62% · 매도 38%`는 주문 잔량 비율이고, 체결강도는 실제 체결된 양의 비율이다. 둘을 같은 걸로 읽지 않게 패널에 계산식(`매수체결 누계 ÷ 매도체결 누계 × 100`)을 적어 뒀다.

### 프로그램매매

키움은 TR마다 금액 단위가 다르다(원, 천원, 백만원). 잘못 잡으면 100만 배 틀린 값이 나오는데, 숫자가 크다 보니 오히려 그럴듯해 보인다. 그래서 `.env`의 `PROGRAM_AMOUNT_UNIT`으로 원 단위로 바꾸고, 화면에 `원본 단위 백만원 가정`처럼 어떤 단위를 가정했는지 표시한다. `NODE_ENV=development`면 원본 값(`raw`)도 같이 내려준다.

순매수는 부호가 전부다. 코드에 가격·잔량용으로 `Math.abs(num(...))` 패턴이 많은데, 이걸 습관처럼 복사하면 순매도 −1,200억이 +1,200억으로 나온다. 그래서 순매수용으로 이름만 다른 `net()`을 따로 뒀다.

프로그램매매는 장 마감 후에 정정되고 휴장일에는 갱신되지 않는다. 값이 없을 때 `0`으로 채우면 화면에 `순매수 0`이 떠서 중립으로 읽힌다. 그래서 기준일자를 같이 보여주고, 오늘 자료가 없으면 `아직 집계되지 않았습니다`라고 표시한다. `DEMO_FLOW_EMPTY=true`로 이 상태를 확인해 볼 수 있다. 차익과 비차익은 의미가 달라서 나눠서 보여주고, 응답에 해당 컬럼이 없으면 그 줄은 숨긴다.

### 해석은 넣지 않았다

`강한 매수세`, `프로그램 순매수 유입` 같은 문구나 상승·하락 색, 화살표는 일부러 넣지 않았다.

- 이 앱은 색을 등락 방향에만 쓴다. 수급 지표를 빨강·파랑으로 칠하면 그 자체로 방향 신호가 된다.
- 체결강도는 누적 비율이라 늦게 반영된다. 120%가 상승을 뜻한다는 근거는 없다.
- 프로그램매매는 미리 등록한 바스켓 주문 방식일 뿐이고 투자 주체와 일대일로 대응하지 않는다. "프로그램 매매 = 외국인"은 흔한 오해다.

대신 계산식과 기준일자를 보여주고 판단은 사용자에게 맡긴다. 방향은 색 대신 `순매수`, `순매도`라는 말로 표시한다.

### 국내 경로의 캐시

원래 캐시는 미국 쪽(`us/gate.js`)에만 있었고, 국내는 `kiwoomRest.js`의 250ms 간격 큐뿐이었다. 그런데 프로그램매매처럼 주기적으로 부르는 기능을 그 큐에 넣으면 같은 큐를 쓰는 차트 조회까지 밀린다. 그래서 캐시, 중복 요청 제거, 토큰 버킷을 `cache.js`로 빼서 두 시장이 같이 쓰게 했다. `us/gate.js`는 이제 이걸 다시 내보내기만 한다.

국내는 분당 호출 수 제한을 따로 두지 않았다. `callTr`이 이미 모든 호출을 순서대로 처리해서, 여기서 또 세면 이중으로 막게 된다. 여기서는 같은 요청을 반복하지 않게 하는 역할만 한다. 순위 응답 30초 캐시도 같은 곳에서 한다. 폴링은 브라우저 탭이 백그라운드면 건너뛰고, 돌아오면 바로 한 번 갱신한다. 캐시가 실제로 호출을 줄이고 있는지는 `/api/flow/stats`에서 볼 수 있다.

|`okRow`|비교용으로 파싱이 된 행의 원본|
|`topLevelFields`|배열 바깥에 합계 같은 값이 있는지|

첫 행만 봐서는 부족하다. 순매수인 날과 순매도인 날에 채워지는 컬럼이 다를 수 있고, 아래의 부호 두 개 문제도 `emptyRow`를 보고서야 찾았다. 디버그 요청은 캐시를 거치지 않는다. 디버그 응답이 캐시에 남으면 다음 일반 요청이 그 값을 받게 되기 때문이다.

### 확인한 TR (ka90013)

종목일별 프로그램매매추이는 `/api/dostk/mrkcond`에 있다(`stkinfo`가 아니다. 짝이 안 맞으면 `1504: 해당 URI에서는 지원하는 API ID가 아닙니다`가 온다).

|컬럼|의미|
|-|-|
|`prm_buy_qty` / `prm_sell_qty`|프로그램 매수·매도 수량|
|`prm_netprps_qty`|순매수 수량(매수 − 매도)|
|`prm_buy_amt` / `prm_sell_amt` / `prm_netprps_amt`|같은 값의 금액. 백만원 단위|
|`prm_netprps_qty_irds`|증감. 순매수와 다른 값이라 `$` 앵커로 구분한다|
|`trde_qty`|그날 전체 거래량. 프로그램 비중 계산에 쓴다|

차익·비차익은 주지 않아서 화면에서 그 줄은 숨겨진다. 금액 단위는 직접 계산해서 맞춰 봤다. `prm_buy_amt` 1,651,052 × 백만원 = 1.65조이고, `prm_buy_qty` 6,637,950주 × 246,000원 = 1.63조로 거의 같다.

### api-id는 꼭 대조해야 한다

체결강도·프로그램매매 TR 4개와 체결강도 FID는 아직 검증하지 못한 값이다. `config.js`에 표시해 뒀고 `.env`로 바꿀 수 있다.

```ini
TR_STRENGTH_TIME=ka10046
TR_PROGRAM_STOCK=ka90013
FID_STRENGTH=228
```

`/api/flow/stats`의 `unverifiedTr`에 목록이 나온다. 데모 모드에서는 이 값을 전혀 쓰지 않아서 화면 확인은 api-id를 맞추기 전에 끝낼 수 있다.

## 미국 증시 탭

상단 `국내 / 미국` 탭으로 바꾼다. 관심종목, 차트, 매매계획은 시장별로 따로 저장된다.

한 화면에 섞지 않고 탭을 나눈 건 시장 규칙이 반대인 게 많아서다.

|항목|국내|미국|
|-|-|-|
|상승 색|빨강|초록|
|호가단위|가격대별 1~1,000원|$0.01(1달러 미만은 $0.0001)|
|일일 가격제한폭|±30%|없음|
|종목코드|6자리|티커(`AAPL`, `BRK.B`)|
|호가창|10단계|무료 API에서 안 줌|
|시세|실시간 WebSocket|15분 지연 REST|

특히 색이 반대인 게 위험하다. 섞어 놓으면 같은 빨강이 어디서는 상승이고 어디서는 하락이 된다. `.shell[data-market='US']`에서 `--up`, `--down` 변수만 뒤집으면 `.up`, `.down` 클래스를 쓰는 곳이 전부 따라 바뀐다.

시장 규칙은 `markets.js`에 모아서 `computePlan`에 넘긴다. 그래서 같은 계산기가 시장마다 맞는 호가단위, 제한폭, 수수료로 계산한다. 미국은 가격제한폭이 없어서 `당일 도달 불가`가 안 나오고, 수수료가 0이라 손익분기 줄도 숨겨진다.

### 시세 공급자

무료 API는 한도와 정책이 자주 바뀌어서 `us/provider.js`로 분리했다. 아래 세 함수만 같은 모양으로 만들면 다른 공급자도 붙일 수 있다.

```
search(query)              -> [{ code, name, exchange }]
quote(symbol)              -> { code, name, price, change, changeRate, ... }
candles(symbol, type, n)   -> [{ time, open, high, low, close, volume }]
```

```
US_PROVIDER=demo          # 키 없이 가짜 데이터
US_PROVIDER=twelvedata    # https://twelvedata.com 무료 가입 (15분 지연)
US_API_KEY=발급받은_키
```

twelvedata 어댑터는 아직 실제 API로 돌려 보지 못했다. 필드명이 다르면 `us/provider.js`의 `quote()`, `candles()` 파싱 부분만 고치면 된다. Finnhub, Alpha Vantage, Polygon 같은 다른 공급자도 같은 자리에 추가할 수 있다.

### 호출 한도

무료 요금제는 분당 호출 수가 아주 적다(Twelve Data 기본 분당 8회). 화면을 한 번 열 때 관심종목, 차트, 계획을 한꺼번에 부르기 때문에 아무 처리도 없으면 바로 한도에 걸린다. 그래서 `us/gate.js`에서 이렇게 막는다.

1. 캐시: 시세 1분, 캔들 1시간, 검색 1시간. 15분 지연 데이터를 매번 새로 받을 이유가 없다.
2. 중복 제거: 같은 요청이 동시에 오면 하나만 보낸다. 관심종목 시세와 선택 종목 시세가 자주 겹친다.
3. 토큰 버킷: 한도를 넘으면 오류를 내지 않고 잠깐 기다렸다 보낸다.
4. stale-while-revalidate: 캐시가 만료돼도 너무 오래되지 않았으면 그 값을 먼저 주고 뒤에서 갱신한다. 15분 지연 데이터라 2분 전 값이 빈 화면보다 낫다.

차트와 매매계획이 같은 길이의 일봉(261봉)을 요청하게 맞춰서 캐시를 같이 쓴다. 길이가 다르면 캐시 키가 갈려 호출이 두 배가 된다. 그 결과 관심종목 4개와 차트 하나인 화면은 5번 호출로 끝나고, `계산하기`를 눌러도 호출이 늘지 않는다.

종목 헤더는 실시간 값, 방금 받은 스냅샷, 관심종목에 이미 있는 값 순으로 보여준다. 마지막 대안이 없으면 호출 한도 때문에 대기하는 동안 관심종목에는 가격이 있는데 헤더만 비어 보인다. 갱신 중일 때는 종목명 옆에 `갱신 중…`이 뜬다. 요금제가 다르면 `.env`의 `US_RATE_PER_MIN`을 고친다.

### 없는 종목 처리

`추가`를 누르면 시세를 실제로 조회해서 값이 오는지 확인한 뒤 목록에 넣는다. 검색 결과만 믿으면 검색에는 나오지만 시세가 없는 종목이 들어간다. 비상장 기업(예: SpaceX)은 티커가 없어서 시세 자체가 없다.

여기서 몇 가지 문제를 겪었다.

- 검색으로 확인하는 흐름과 시세로 확인하는 흐름이 따로 돌 때, 시세 확인이 호출 한도 대기열에 걸린 사이 검색 쪽이 먼저 "없습니다"를 띄웠다. 알림과 `확인 중…` 버튼이 동시에 보였다. 지금은 `addCode`가 성공 여부를 돌려주고 `submit()`이 그걸 기다린다. 실패하면 입력을 지우지 않아서 뭘 시도했는지 볼 수 있다.
- 빠르게 입력하고 바로 `추가`를 누르면 디바운스 검색이 끝나기 전이라 검색을 안 한 것으로 판단하고 그냥 통과시켰다. 지금은 `submit()`이 필요하면 검색을 직접 기다린 뒤 판단한다.
- 알림을 띄운 뒤 늦게 끝난 검색이 드롭다운을 다시 열어서 알림을 가렸다. `noticeFor`로 막았다.
- 보고 있던 종목을 지우면 선택도 다른 종목으로 옮긴다. 이걸 안 하면 목록에서 지운 종목 시세를 계속 조회하면서 헤더에 남는다.

검색이 호출 한도(429)나 타임아웃(408)으로 실패하면 시세 확인으로 넘어가지 않고 바로 `호출 한도 대기 중입니다`라고 알린다. 같은 대기열에 막혀 있으니 10초를 더 기다리게 할 이유가 없다. 미국 탭에서 티커를 직접 넣었는데 검색은 성공하고 결과가 0건이면 추가를 막는다. 검색 자체가 실패했을 때는 판단할 근거가 없어서 시세 확인으로 넘긴다. 안내 문구는 시장별로 다르게 나온다. 미국 탭에서 `6자리 코드로 입력해 주세요` 같은 국내 안내가 나오면 안 된다.

확인용 조회는 10초, 일반 조회는 25초에서 끊는다. 버튼 앞에서 기다리는 요청이라 오래 붙잡을 수 없다. 확인 조회 결과는 캐시돼서 바로 뒤 스냅샷 조회가 재사용한다. 이미 관심종목에 있는 종목이 빈 시세를 주거나 응답이 8초를 넘기면 원인을 안내하고 삭제 버튼을 띄운다. 그렇지 않으면 대기열에 막힌 동안 사용자가 아무것도 못 하게 된다.

### 미국 탭에 없는 것

- 호가창: 무료 시세 API가 주지 않는다.
- 거래량·등락률 순위: 키움 순위 TR은 국내 전용이다.
- 분봉: 무료 요금제는 대부분 일봉부터 준다.
- 실시간: 15분 지연이다. 상단에 표시된다.

### 세금

미국 주식은 양도소득세(연 250만 원 공제 후 22%) 대상이고 1년 단위로 정산하기 때문에 국내처럼 매매 한 건마다 손익분기에 넣을 수 없다. 그래서 미국 탭의 기본 거래비용은 0이고 손익분기 줄도 나오지 않는다. 환율 변동도 반영하지 않고 수량은 달러 기준으로 계산한다.

## 설계하면서 정한 것들

실시간 연결은 하나만 쓴다. 키움은 연결당 등록할 수 있는 종목 수에 제한이 있어서, 서버가 키움과 연결 하나만 열고 브라우저들에 나눠 준다. 종목별 구독자 수를 세서 아무도 안 보는 종목만 해제(REMOVE)한다. 브라우저 탭을 여러 개 열어도 키움 쪽 등록은 늘지 않는다.

키움이 보내는 `{"trnm":"PING"}`은 그대로 돌려보내야 한다. 안 그러면 연결이 끊긴다.

응답 파싱은 느슨하게 했다. TR마다 배열이 들어 있는 키 이름이 다르고(`stk_dt_pole_chart_qry` 등) 문서가 개정되면서 바뀌기도 한다. `firstArray()`는 응답에서 첫 번째 배열을 찾아서 쓰고, 호가는 `sel_3th_pre_bid` 같은 키를 정규식으로 찾는다. 필드명 하나가 바뀌어도 전체가 죽지는 않는다.

종목코드는 6자리로 맞춘다. 넥스트레이드가 생긴 뒤로 키움이 `233740_AL`(통합), `005930_NX`(넥스트레이드), `005930_KR`(한국거래소)처럼 거래소 구분을 붙여서 주는데, 이걸 그대로 시세 조회에 넣으면 빈 값이 온다. `normalizeCode()`가 뒤를 떼고 6자리만 남긴다. 순위·마스터 응답과 라우트로 들어오는 코드 양쪽에 적용하고, 화면 쪽에도 같은 규칙이 있어서 예전 버전이 저장해 둔 코드도 정리된다.

숫자는 `"+1,200"`, `"-500"`처럼 부호와 콤마가 섞인 문자열로 온다. 가격과 잔량은 절댓값으로, 전일대비와 등락률은 부호를 살려서 읽는다.

부호가 두 번 붙어 오는 경우도 있었다. 키움이 등락 방향 부호를 앞에 붙이는데, 값이 원래 음수면 이렇게 된다(ka90013에서 실제로 봤다).

```
prm_buy_qty      5469274
prm_sell_qty     5833738
prm_netprps_qty  "--364464"   ← '-' + '-364464' = -364,464
```

`Number("--364464")`는 `NaN`이다. 처음 만든 `num()`은 이걸 `null`로 버렸는데, 그 결과 순매도인 날이 통째로 빠져서 20거래일이 전부 순매수처럼 보였다. 화면에는 그럴듯한 양수만 남아서 눈으로는 알아채기 어려웠다. 지금 `num()`은 앞쪽 부호 중에 `-`가 하나라도 있으면 음수로 본다. 개수로 홀짝을 따지면 안 된다. `--364464`는 마이너스가 두 개지만 음수다.

프로그램매매는 매수와 매도를 따로 주기 때문에 `매수 − 매도`로 순매수를 구할 수 있다. 순매수 컬럼을 못 읽으면 이 값으로 대신하고, 응답의 `netSource`가 `derived`로 바뀐다. 화면에도 경고가 떠서 파싱이 어긋난 걸 알 수 있다.

## 확인이 필요한 부분

`config.js`의 api-id와 `realtime.js`의 FID 번호는 공식 문서와 꼭 대조해야 한다. 키움은 TR 코드와 필드명을 자주 바꾸고, api-id가 틀리면 `return_code != 0`으로 조용히 실패한다. 서버 로그에 `키움 API가 실패를 반환했습니다`가 보이면 대부분 이 문제다.

디버깅할 때는 `NODE_ENV=development`로 서버를 띄우면 `/api/quote/:code` 응답에 키움 원본(`raw`)이 같이 와서 실제 필드명을 바로 볼 수 있다.

## 화면 규칙

- 상승은 빨강, 하락은 파랑이다. 한국 시장 관례이고 서양식(초록/빨강)과 반대다.
- 색은 등락 방향에만 쓴다. 나머지는 전부 무채색이라 화면에 빨강이 보이면 무조건 오른 것이다.
- 숫자는 전부 고정폭 글꼴과 `tabular-nums`를 써서 자릿수가 세로로 맞는다.
- 체결이 들어오면 해당 줄이 400ms 동안 깜빡인다. `prefers-reduced-motion`을 켠 사용자에게는 깜빡이지 않는다.

## 다음에 해 보고 싶은 것

- 시장 전체 프로그램매매 패널. 라우트(`/api/program-market`)는 있는데 화면이 없다. 지금 레이아웃은 선택 종목 중심이라 시장 단위 데이터를 둘 자리가 마땅치 않다. 하단 순위 패널 옆이나 상단바를 생각하고 있다.
- 투자자별 매매동향(외국인, 기관). 프로그램매매와는 다른 데이터다. 프로그램매매는 주문 방식이고 이건 주체 구분이다.
- 서버를 여러 개 띄우게 되면 `cache.js`를 Redis로 바꿔야 한다. 인터페이스(`run`, `stale`)는 그대로 두면 된다.
- 주문 기능은 신중하게 생각해야 한다. 계좌 인증과 주문 TR이 따로 있고, 실수했을 때의 비용이 시세 조회와는 비교가 안 된다.
